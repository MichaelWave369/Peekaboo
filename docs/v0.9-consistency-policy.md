# Peekaboo v0.9 acquisition consistency policy

Peekaboo treats an adaptive multi-shard scan as one evidence acquisition. A successful HTTP response from every shard is necessary, but not sufficient, for the merged dataset to be accepted.

## Shared-boundary duplicates

A single OpenStreetMap object can legitimately appear in more than one shard when it lies on or overlaps a shard boundary.

Peekaboo canonicalizes normalized record payloads before comparing duplicates. Object-key ordering does not affect the comparison.

- Same OSM object ID + canonically identical payload: deduplicate safely.
- Same OSM object ID + different payload: reject the merged acquisition.

Peekaboo does not pick the first copy, the newest copy, the highest version, or attempt to synthesize a consensus record.

## Why fail closed?

Adaptive shards are fetched sequentially. An OSM object can be edited while the scan is in progress, meaning two individually valid shard responses may describe different revisions of the same object.

Silently choosing one revision would create a dataset whose provenance depends on request ordering rather than a stated evidence rule.

A consistency conflict therefore produces `SHARD_CONSISTENCY_CONFLICT` and no merged dataset is accepted. Previously loaded known-good data remains available through the existing query-failure behavior.

## Conflict receipt

The consistency error carries a bounded receipt containing:

- OSM object ID;
- first shard ID;
- second shard ID;
- OSM version from each copy when available;
- source timestamp from each copy when available;
- changeset from each copy when available;
- coordinates from each copy when available.

The receipt is diagnostic evidence about the acquisition conflict. It does not establish which physical-world state is correct.

## Canonical comparison

Canonical comparison recursively sorts object keys while preserving array order and primitive values. This prevents harmless JSON/object key-order differences from manufacturing false conflicts.

The comparison is exact over the normalized record payload. A meaningful difference in tags, geometry, source revision metadata, classification, vendor evidence, or other normalized fields is treated as disagreement.

## Completeness invariant

For an adaptive scan to be accepted:

1. all expected shards must complete;
2. the combined unique-record count must remain under the browser safety ceiling;
3. duplicate IDs across shards must have canonically identical payloads;
4. only then may duplicate boundary records be collapsed and the dataset displayed.

This policy describes consistency of public OpenStreetMap records acquired during one scan. It does not convert OSM metadata into independent verification of physical surveillance infrastructure.
